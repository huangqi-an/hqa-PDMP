# worker-service 任务队列设计笔记

> 本文回答一个核心问题：为什么 worker-service 会先使用 Redis List，再升级到 Redis Streams。
> 重点是知识框架，而不是具体代码。当前 worker-service 已迁移到 Redis Streams，Redis List 版本仅作为学习路径中的对照保留。

## 1. 任务队列到底在解决什么问题

HTTP 接口适合处理“快请求”：收到参数、做点计算、返回结果。但有些任务不适合让请求一直等：

- 任务耗时较长，例如调用模型、处理文件、批量发送通知；
- 任务可能失败，失败后需要重试；
- 任务数量可能瞬间很多，需要多个后台 worker 分摊处理。

如果把这些任务放在请求处理函数里直接执行，就会出现：

- 客户端长时间等待，甚至超时；
- 请求占住连接和进程资源；
- 一次请求失败，任务就跟着失败，没有“稍后重试”的余地。

任务队列的核心思路是“先收下来，再慢慢做”：

1. 接口收到任务后，只负责写入队列；
2. 后台 worker 从队列里取出任务并处理；
3. 客户端通过另一个接口查询任务状态和结果。

这背后的通用角色有三个：

| 角色 | 本项目中的位置 |
| --- | --- |
| Producer 生产者 | `TaskHandler.Create`，负责接收请求并入队 |
| Queue 队列 | Redis，负责暂时保存待处理任务 |
| Consumer 消费者 | `worker.Run` 启动的多个 goroutine |

## 2. 一个任务队列至少要具备哪些能力

从当前代码看，worker-service 已经体现了四个基本能力：

1. **入队**：创建任务后，任务能进入队列；
2. **消费**：worker 能拿到任务并处理；
3. **状态查询**：任务是否还在排队、正在运行、已完成或失败；
4. **并发消费**：多个 worker 可以同时消费，不会重复或遗漏。

List 版本和 Streams 版本的差别，主要在第 2 点和第 4 点上。

## 3. 为什么第一版选择 Redis List

Redis List 是最容易理解的一种“队列形状”。

它的模型很直观：

- 生产者从列表左边塞入任务；
- 消费者从列表右边取出任务；
- 队列中没有任务时，消费者可以阻塞等待，而不是空转。

在 Redis 命令层面，对应的是：

| 命令 | 作用 |
| --- | --- |
| `LPUSH` | 从左边写入队列 |
| `BRPOP` | 从右边阻塞取出一个任务，没有任务时等待 |

选择 List 作为第一版，不是为了最终生产可靠，而是为了用最小的认知成本跑通“生产者 + 消费者”这条链路。

这一步真正练到的是：

- Go 中如何用 goroutine 常驻消费任务；
- 阻塞式 IO 是什么，为什么不能让 worker 空转；
- 如何把 Redis 命令封装成 `TaskStore` 的方法；
- 如何用 `context` 控制 worker 停止。

所以 List 版本更像“任务队列的最小闭环”，它让整条链路先跑起来。

## 4. Redis List 的边界在哪里

List 可以当队列，但它不是为“可靠任务队列”设计的。

最大的问题是：`BRPOP` 取走任务的同时，任务就从 List 中消失了。

这意味着 worker 的流程是：

```text
取出任务
  -> 任务从队列消失
    -> 处理任务
      -> 写入状态
```

如果 worker 在“取出任务”之后、“处理完成”之前崩溃，这个任务会直接丢失。因为队列里已经没有它了，也没有任何地方记录“它正在被某个 worker 处理”。

此外，List 版本很难表达下面这些问题：

- 这个任务被谁领取了？
- 处理了多久？
- 哪些任务已经读走但没有确认完成？
- worker 崩溃后，已领取的任务如何重新分配？

这些不是第一版需要马上解决的问题，但它们是真实任务队列必须面对的问题。

所以可以这样理解：

- List 版本主要练“能把任务跑起来”；
- 它默认了“任务被取出后不会丢”这一假设；
- 一旦要讨论可靠性和失败恢复，这个假设就站不住了。

## 5. 为什么下一步是 Redis Streams

Redis Streams 可以理解为“带消费组和确认机制的消息流”。

和 List 最大的区别是：**任务被读走后，不会立刻删除。**

它引入几个关键概念：

| 概念 | 含义 |
| --- | --- |
| Stream | 一条只追加的消息流 |
| Consumer Group | 一组消费者，共同消费一个 Stream |
| Consumer | 消费组中的一个具体消费者实例 |
| Pending | 已读但尚未确认的消息 |
| Ack | 消费者处理成功后，向 Redis 确认 |

一个典型的消费流程变成：

1. 生产者把任务写入 Stream；
2. 某个 consumer 从消费组里读取任务；
3. 任务进入 pending 状态，但不会从 Stream 中删除；
4. consumer 处理成功后执行 ack；
5. Redis 才认为这条消息处理完成。

如果 consumer 在 ack 之前崩溃，任务会继续留在 pending 中。之后可以通过 pending 信息排查它，或在一定时间后重新分配给其他 consumer。

这就是所谓的 **at-least-once** 语义：任务可能被处理多次，但不会因为“读走就丢失”而凭空消失。为了处理“可能重复”的问题，业务侧需要尽量保证任务幂等。

在 Redis 命令层面，主要对应：

| 命令 | 作用 |
| --- | --- |
| `XADD` | 向 Stream 追加一条消息 |
| `XGROUP CREATE` | 创建消费组 |
| `XREADGROUP` | 以消费组身份读取消息 |
| `XACK` | 确认一条消息已处理完成 |
| `XPENDING` | 查看待确认的消息 |

升级到 Streams，不只是换几个命令，而是学习一套通用模式：

- 为什么消息需要确认；
- 为什么消费者要属于某个组；
- 什么是 pending，为什么它重要；
- worker 崩溃后如何恢复和重试；
- 多个 worker 如何分工消费。

这套模式在 Kafka、RabbitMQ、AWS SQS 等系统中都有对应概念，学会之后不是只会用 Redis。

## 6. List 与 Streams 的对比

| 维度 | Redis List 版本 | Redis Streams 版本 |
| --- | --- | --- |
| 数据结构 | List | Stream |
| 读走后是否删除 | 是 | 否 |
| 是否支持确认 | 否 | 是，`XACK` |
| 是否支持消费组 | 否 | 是 |
| 任务是否会因 worker 崩溃而丢失 | 可能丢失 | 保留在 pending，可恢复 |
| 多 worker 分工 | 基本靠 `BRPOP` 竞争 | 消费组统一分配 |
| 学习重点 | goroutine + 阻塞消费 | 消费组 + ack + pending |

## 7. 为什么分两步学习，而不是直接写 Streams

如果直接写 Streams，你会同时接触：

- Go goroutine；
- Redis Streams；
- 消费组；
- ack；
- pending；
- 失败重试。

概念太多时，很容易变成“照着代码抄，但不知道每部分为什么存在”。

分两步的好处是：

1. 先用 List 跑通最小闭环，理解“入队 -> 消费 -> 查询状态”；
2. 再引入 Streams，只替换“消费和确认”这一层；
3. 通过对比，才能看出 Streams 到底解决了什么问题。

所以 List 版本不是白写。它是你理解 Streams 价值的对照物。

## 8. 当前 Streams 改造已经抓住的知识点

Streams 改造不需要把所有代码推倒重来，关键是抓住下面几个点：

- 入队从 `LPUSH` 改为 `XADD`；
- worker 启动前先确保消费组存在；
- 每个 goroutine 使用不同的 consumer 名字；
- worker 读取时使用 `XREADGROUP`，而不是 `BRPOP`；
- 任务处理成功后显式 `XACK`；
- 保留任务的 Hash 状态记录，继续支持 `GET /api/tasks/:id` 查询。

完成这些后，可以继续练习：

- 查看 pending 消息；
- worker 优雅退出时等待正在处理的任务完成；
- 模拟 ack 前崩溃，再观察 pending 如何保留任务；
- 为失败任务设计重试策略。

## 9. 一句话总结

Redis List 让任务队列“先跑起来”，Redis Streams 让任务队列“更接近真实生产”。前者的价值是建立最小闭环，后者的价值是学习消费组、确认与失败恢复。
